---
title: Applying updates
description: How the app's files are replaced once it has exited.
---

A running app cannot reliably replace its own files, least of all on Windows, where open files are locked. So the app hands its verified download to a small helper process (`rethinkj-updater-helper`) and exits. The helper waits until the app has exited and replaces its files, so that the app's folder holds either the old or the new version in full.

An update can come as an archive of the whole app (zip or tar.gz), as a single JAR, or, later, as a native installer that the helper runs. So far the helper replaces an archive or a JAR. If the app asks for it, the helper starts the new version and keeps it only once it confirms that it runs.

core and the helper work together through files in an update folder the app names; [Helper files](/docs/reference/helper-files) describes them.

## From the app

Ship the helper JAR with the app, on its class path: add `rethinkj-updater-helper` beside `rethinkj-updater-core`, with the same version. The app never calls it; core finds it there and starts it.

`Installation` stands for the installed app: its folder, or its JAR if the app is a single JAR, and the update folder, which lies outside the app's folder and is the same for every version, such as `updates` in `%LOCALAPPDATA%\MyApp`. An app started by a launcher that jpackage built gets both from the launcher:

```java snippet="installation"
```

Otherwise `new Installation(app, updates, command)` names the app's folder, the update folder and the command that starts the app.

When the app starts, `result()` reports what the helper did with the last update, once. Its `status()` is `APPLIED`, `ROLLED_BACK` or `REJECTED`, and `reason()` is one of the [reason codes](/docs/reference/helper-files#result):

```java snippet="result"
```

Once the app is ready for use, it confirms that it runs. A version the helper has just started is kept only if it does; at any other start this does nothing. Confirm after the app has shown its first frame rather than as it starts, so that a version whose window fails to come up is rolled back:

```java snippet="confirm"
```

Before it downloads an update, the app asks whether the user may write to its folder and the folder above it. Without that, the helper cannot replace the app, and asking for rights is not implemented yet:

```java snippet="writable"
```

With the [download](/docs/get-started/check-for-updates#download-and-verify), the app starts the helper:

```java snippet="apply"
```

- `replaceOnExit(download)`: the helper waits until the app exits, whenever that is, replaces it and does not start it again.
- `restart(download)`: the app exits next, as soon as it safely can. The helper replaces it and starts the new version with the command. If that version does not confirm within two minutes, or exits before, the helper ends it with every process it started, puts the old version back and starts that. A process it cannot see, because it was started and orphaned between two of the helper's checks a tenth of a second apart, outlives the rollback. If the helper changed nothing, because a file stayed locked for instance, it starts the old version as well. It writes the result before it starts the old version, so that version reports it at once; a new version that confirmed reports `APPLIED` at its next start, since the helper writes it once the confirmation arrives.

The download stays where it is; the app deletes it, for instance once `result()` reports.

### How core starts the helper

- It takes the helper JAR from the app's class path, or from its module path if the module `com.rethinkj.updater.helper` is resolved, for instance with `--add-modules`. `withHelper(jar)` names it instead. A JAR whose manifest does not list the plan formats is not run.
- It copies the JAR into a new folder `helper-<n>` in the update folder. If the app runs on a runtime in its own folder, as a jpackage or jlink image does, it copies that runtime there as well and starts the helper on the copy. Otherwise the helper runs on the app's runtime.
- The runtime needs `bin/java`, `bin\java.exe` on Windows. jpackage leaves it out of the runtime it builds, unless `--jlink-options` are given without `--strip-native-commands`, such as `--jlink-options "--strip-debug --no-man-pages --no-header-files"`. Without it, starting the helper throws.
- It writes the plan and starts the helper in that folder. The helper prints nothing; should its JVM fail to start, what it says ends up in `helper.log` in the update folder.
- On Linux the helper runs in a session of its own, through `setsid`, so that it outlives the terminal the app was started from.

The command comes from the installed version and starts the new one, in the update folder as its working directory. Its process must run as long as the app does, as a jpackage launcher does; a script that starts the app and exits counts as an app that exited. If a new version renames its launcher, the command finds no launcher, and every update to it is rolled back.

Once no helper is at work, `result()` deletes the helper's copies. One that Windows still holds open, while the helper exits, is deleted at a later call.

While a helper is at work, until it has written its result, starting another one throws an `IllegalStateException`, as does a second start from the same process. Starting a helper deletes a result nobody has read, so a version that schedules the next update soon after it confirmed reads `result()` first, once the helper is done. Two copies of the app must not share an update folder.

## How the helper replaces an app

1. It checks the download's SHA-256 again, since hours may pass between the download and the app's exit.
2. It builds the new version beside the app's folder, as `<app>.new-<n>`, and carries over the files that belong to the user, not to the app.
3. It renames `<app>` to `<app>.backup-<n>`, and `<app>.new-<n>` to `<app>`. If the second rename fails, it renames the backup back.
4. With `restart`, it starts the new version and waits for its confirmation. Without one, it renames the new version aside and the backup back to `<app>`, the same way, and deletes the new version.
5. Once the new version is in place, and with `restart` has confirmed, it deletes the backup, and of a link or a Windows junction in it only the link.

While a rename fails, because another process has a file open, such as a virus scanner on Windows, the helper tries again for 30 seconds before it gives up, with the reason `locked`. A single JAR is replaced the same way: the new JAR is written beside it, then the two are renamed.

If the helper is ended before the renames, when the user logs off for instance, nothing has changed. If it is ended between the two renames, or cannot rename the old version back, the app's folder is missing and the old version is in `<app>.backup-<n>`. What the helper cannot delete, as a file that Windows holds open, stays beside the app's folder, where it is in the way of nothing.

## The app's own files

The helper tells the app's files from the user's by `rethinkj-updater.files`, the [file list](/docs/reference/helper-files#file-list) in the app's folder. It writes the list of each new version. So that the first installation brings one, write it into the app's folder once the app is built, before it is packed:

```sh
java -jar rethinkj-updater-helper.jar list <folder>
```

- A file the list names is replaced by the new version, or dropped if the new version does not have it.
- Any other file, such as settings the app keeps in its folder, is carried over into the new version, also in place of a file of the same path that the new version brings. The new list does not name it either. If the new version makes the folder that holds such a file a link, the helper rejects the update and changes nothing.
- Without a list, the new version's files replace the old ones, and no file is dropped.

## Archives

- zip on Windows, tar.gz on Linux, where only tar keeps which files are executable.
- If the archive holds a single folder at its top, such as `myapp-1.3.0/`, its contents become the app's folder.
- Files from a tar keep their permissions, except that only their owner may write them, at most `0755`. Folders get the system's default permissions.
- A symbolic link in a tar stays a link if it leads to a file or folder in the app's folder, such as the links between the legal notices in the runtime of a jpackage or jlink image on Linux. A link in a zip comes out as a small file holding the link's target, since Java cannot tell the two apart in a zip.
- The helper rejects an archive that holds any other link, a hard link, a path that leads out of the app's folder, a sparse file or a file over 8 GB.
